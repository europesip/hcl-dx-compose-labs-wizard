2 · Access to DX

⚠ nginx is only for clusters that already run ingress-nginx, such as older RKE2 versions (which installed it by default) or a k3s installed with --disable traefik. The Kubernetes project retired ingress-nginx in March 2026: if in doubt, choose traefik, the controller that k3s installs by default.

With nginx or traefik the labs publish DX ready to use (an Ingress or a Traefik IngressRoute that re-encrypts towards the DX HAProxy). IQ chains several LLM calls for every question, and each one carries ~30,000 tokens of HCL system prompt and tool definitions, so it is expensive even with prompt caching. In all three the installed result is the same, and the wizard only generates files: it never talks to your cluster.

Option A · Only env.sh

Just the configuration file the labs need. Then follow the labs manually, with the guide of each lab (GUIDE.md / GUIDE.es.md).

Option B · env.sh + RUNBOOK.md

A ZIP with env.sh and RUNBOOK.md: the instructions to build, one after the other, the labs you selected, with the scripts to run and the equivalent commands using your values.

Option C · Direct installation (dx-install/)

A self-contained folder, a tailor-made installation you can even send to someone without the labs repository: every file already filled in with your values (credentials included, in plain text), a RUNBOOK.md with short, easy-to-follow commands and an install.sh that runs them showing the lab and step.

A and B: put the files in the root of your clone of the repository (next to env.example.sh) and source ./env.sh; the lab scripts install everything. C: unzip it anywhere (it creates dx-install/), then cd dx-install and follow its RUNBOOK.md or run ./install.sh. Option C contains credentials in plain text: keep it private and rotate them afterwards.

Why OpenRouter?

OpenRouter is not in the HCL configuration guides, which use AWS Bedrock. It is an option we are validating in these labs (IQ works with it on CF238 and CF239), and it behaves like AWS Bedrock: a cloud service that gives access to many LLMs through a single API, so you can choose the model behind IQ.

Why not Bedrock for a PoC? Signing up for AWS Bedrock is laborious: an AWS account, IAM users and policies, access requests for each model, regions… OpenRouter offers the same functionality with a practical, comfortable interface: one account, one API key, and you can choose and try many AI models, all billed in a single place. That makes it very suitable for PoCs and labs.

Sovereign AI. We are aware of how important sovereign AI is, and it is one of our main concerns. That is why we also value this: besides the large models of today's vendors (Claude, GPT, Gemini…), OpenRouter offers open-weight models (Qwen, DeepSeek, Mistral, gpt-oss…) that you can later download and run on your own hardware. You can test them with IQ first, at almost no cost, and then decide whether to move to a local model so that your data never leaves your infrastructure.

Getting started. If you do not have an account yet, sign up at openrouter.ai, create an API key and buy credits: about €10 is enough for a PoC. If you already have an API account with Anthropic (Claude) or another provider (OpenAI, Google, AWS Bedrock, Azure), you do not even need to buy credit: OpenRouter can use your own key for that provider (BYOK), so the usage is charged to the credit you already have there. OpenRouter's BYOK fee is free up to a monthly allowance far above what a PoC uses. OpenRouter lets you set a spending limit on each key and shows every request with its tokens and cost in its activity page, so you always know what you are spending.

External dependencies

Four pieces that are not HCL software and that some labs use. They go in the shared namespace (dx-shared), apart from DX, and they are installed first, before Lab 1.

  • OpenLDAP: a directory with demo users and groups. Lab 2A connects DX to it.
  • PostgreSQL 18 (CloudNativePG operator): for the IQ chat sessions (Lab 3 appendix), or for your own advanced uses.
  • LiteLLM: the proxy between IQ and the AI models, through OpenRouter. Lab 3A needs it.
  • EUROPESIP MCP Server: our own tools for IQ. Lab 3B needs it.

Why first? With them already in place, the labs only connect DX to them, and the demo goes faster.

If you do not install one, the labs that need it are not available (they appear disabled), or you give the details of the one you already have: an existing Active Directory instead of OpenLDAP (Lab 2A), an existing Oracle as the Web Engine database (Lab 2B).

When to use PostgreSQL for the Web Engine

Right now the Web Engine can use PostgreSQL only if you create yourself the tables it needs, following the steps HCL gives you. Those steps are not supplied with the lab yet, because they have not been validated yet.

If you have them, choose PostgreSQL:

  • PostgreSQL is installed in the external dependencies, before anything else.
  • Before that step you put the table creation script, setup-postgres-dx.sql, where the RUNBOOK.md tells you: the cluster runs it once, when it is created.
  • Lab 2B then transfers the Web Engine data from Derby to PostgreSQL (~14 min).

If you do not have them, use Derby, the internal database of the product (default, nothing to do), or an existing Oracle. PostgreSQL can still be installed for other advanced options, such as the IQ sessions in the database (Lab 3 appendix).

Lab 1B · Sample Script Application

A Script Application is HTML, JavaScript and CSS stored in WCM: the way to build your own applications on DX Compose without Java portlets (which need the separately licensed Java Transition Module).

This lab deploys Hello DX, a small React app by EUROPESIP, with a Helm chart: a Kubernetes Job runs HCL DXClient and pushes the app into WCM. No DXClient or developer tools on your PC: just helm. Every later run updates the same app.

It shows two integrations with the DX REST APIs, as the signed-in user: who is signed in, and which WCM libraries they can read.

After the install, add it to a page once: edit a page, add a component, Script Applications → Hello DX. Source, chart and instructions: github.com/europesip/hcl-dx-scriptapp-helm.

Lab 5 · ÓRBITA, an advanced application

An advanced lab, not needed for the installation of DX Compose: it shows what a real application on DX Compose looks like. ÓRBITA is an intranet suite by EUROPESIP: time tracking (also from a kiosk with a PIN or QR card), time off, expenses and travel (receipts read by in-browser OCR), approvals with conversations and notifications, and a home page with each person's day.

  • Script Applications: six React apps pushed to WCM by a Helm chart (DXClient), each on its own page under Home.
  • Microservice: a REST API (Open Liberty) on the DX host. It asks DX who the user is with their own session: no shared keys or stored passwords.
  • Persistence: its own database in the PostgreSQL of the external dependencies, with schema migrations (Flyway).
  • AI integration: an MCP server with 26 tools. Registered in the IQ Integrator (with a patch, because of the same IQ bug as in Lab 3B), the IQ assistant answers and acts on ÓRBITA as the user asking, in English or Spanish.

The demo users are those of the Lab 2A OpenLDAP (macarena, andres, german, patricia…). Public chart and images, about 3 minutes. Guide: lab5-orbita/GUIDE.md · source: github.com/europesip/orbita.

Installation mode

Step by step (to learn): the labs in order, each one adding its layer to DX. Every lab that changes DX runs a helm upgrade of DX, and each one restarts the Web Engine (~5 min).

Fast demo (when time is short): the same result in the fastest order.

  1. The external dependencies, first.
  2. DX installed once, already connected to its directory (Lab 1 + 2A).
  3. IQ and search installed right after.
  4. One single DX upgrade that enables IQ and search together.
  5. Lab 1B and the checks.

About 15 minutes less with every lab (two DX upgrades fewer). Not available with the Oracle transfer (Lab 2B): use step by step for it.

From the repository, the fast demo is common/demo-fast.sh: the env.sh of this wizard already carries your choice.
